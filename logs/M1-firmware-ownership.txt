Who owns the five firmware names now — a reverse-dependency scan, run 2026-10-31 (02:3x, against
the build host's own trixie indices while the post-amendment rebuild was in its install pass).

=== the question, and why the claim needed a run ===

docs/SPEC.md §5's 2026-10-31 amendment says the enablement packages are "named because nothing else
names them any more", and logs/M1-firmware-chroot-off-run.txt §4 shows the five arriving as
"additional packages" of the new build. Both of those say the same thing: the image carries them
because `manifests/base.pkgs` does. That is only worth amending the spec for if deleting a line from
`base.pkgs` really deletes a package from the image — otherwise the manifest is decoration on top of
an edge that some other package controls, and §5 would be claiming control it does not have.
The test for that is a reverse-Depends scan: if the archive itself has an edge to one of these names,
our line is not what keeps it.

=== method ===

  Script: throwaway, this run only. Files scanned, read-only, exactly the four index files already on
  the host from the main-only /etc/apt/sources.list.d/0000debian.sources:

    deb.debian.org_debian_dists_trixie_main_binary-amd64_Packages                 56 620 099 B
    security.debian.org_debian-security_dists_trixie-security_main_binary-amd64_Packages 1 855 409 B
    deb.debian.org_debian_dists_trixie-backports_main_binary-amd64_Packages        2 074 082 B
    deb.debian.org_debian_dists_trixie-updates_main_binary-amd64_Packages              1 406 B

  `Depends:` and `Pre-Depends:` fields are tokenised — split on ",", each token trimmed, " ( version
  )" clause dropped, ":arch" qualifier dropped — and compared for **equality** against the name. A
  substring grep would have matched `firmware-linux-free` inside `firmware-linux-nonfree` and printed
  a confident wrong answer, which is the failure mode this whole milestone keeps hitting.
  Total edges collected: 335 894.

=== result ===

    firmware-linux-free    nothing in these indices Depends or Pre-Depends on it
    firmware-ath9k-htc     nothing in these indices Depends or Pre-Depends on it
    firmware-carl9170      nothing in these indices Depends or Pre-Depends on it
    alsa-topology-conf     nothing in these indices Depends or Pre-Depends on it
    indi-dsi               nothing in these indices Depends or Pre-Depends on it
    wireless-regdb         ONE dependent: reform-desktop-minimal

  and all five are in the Depends: of the package this project builds:

    dpkg-deb -f /opt/phantomos-build/pool/phantomos-base_0.1.0-1_all.deb Depends
      ... phantomos-release phantomos-config sudo unattended-upgrades apparmor nftables lvm2
          cryptsetup ca-certificates apt-listchanges openssh-client flatpak
          linux-image-amd64 firmware-linux-free firmware-ath9k-htc firmware-carl9170
          wireless-regdb alsa-topology-conf
    indi-dsi is not in that list. It is in manifests/drops.pkgs.

  So: for four of the five, the only edge into the image is ours. `wireless-regdb` has one
  third-party dependent in the archive, `reform-desktop-minimal`, which is not in §5's selection and
  is not pulled by anything that is — the scan checked that, and `phantomos-base`'s Depends: line
  above is the complete list of what this project names. Its other documented route is a
  `Recommends:` of `network-manager` (§12 item 12), and Recommends are off in this build
  (`--apt-recommends false`, plus live-build's own `-o APT::Install-Recommends=false` in
  functions/packages.sh:56), so that route is closed. Naming it is load-bearing.

  The claim in §5 is therefore true in the direction it matters: delete the line, the package goes.

=== what this scan does NOT cover, stated because the limits are load-bearing ===

  - The universe is **main**, the four files above. `contrib` and `non-free-firmware` indices are not
    on this host (they were fetched read-only over HTTPS for logs/M1-firmware-areas.txt and
    logs/M1-firmware-nonfree-scale.txt, which counted packages and paths, not dependency edges).
    That is the right universe, not a shortcut: --archive-areas main means an edge from a package
    outside main could not be resolved by this build anyway. If §12 item 11 opens the area, this scan
    has to be re-run against it, because a non-free package could Depends: on one of these names and
    silently make our line redundant.
  - Only `Depends:` and `Pre-Depends:`. `Recommends:`, `Suggests:`, `Enhances:` and `Package: …`
    multi-line virtual-provider tricks are not scanned. That is deliberate: with Recommends off, a
    Recommends edge is not a route into the image, and the question was "can this package arrive
    without our line", which for this build only Depends/Pre-Depends can answer.
  - This is a statement about the archive's index, not about the booted image. The image-side answer
    is `scripts/m1-diff.sh` (a §5 name that is absent fails direction 1) plus
    `harness/commands/M1.txt`'s `dpkg -l` line on the running machine.

=== one incidental finding from the same index read, kept because it is the kind that bites ===

  `linux-image-amd64` appears in three stanzas of the files scanned, because backports is one of the
  four:

    Version: 6.12.107-1              Depends: linux-image-6.12.107+deb13-amd64 (= 6.12.107-1)
    Version: 6.12.113-1              Depends: linux-image-6.12.113+deb13-amd64 (= 6.12.113-1)
    Version: 7.2.11-1~bpo13+1        Depends: linux-base-amd64 (= 7.2.11-1~bpo13+1),
                                               linux-image-7.2.11+deb13-amd64 (= 7.2.11-1~bpo13+1)

  So a build host with a backports index can resolve the same name to a kernel three minor versions
  ahead of the release. What the pre-amendment image actually installed is measured, from its own
  dpkg database (logs/pre-config-image-installed.txt) and its build log
  (`Setting up linux-image-6.12.113+deb13-amd64`): **6.12.113+deb13-amd64**, the stable kernel, not
  the backport. That matches §6.4 ("Debian's kernel as shipped, no rebuild") and matches the
  running M0 guest, which booted 6.12.113+deb13-amd64 (§3.1's "as booted" row).
  The post-amendment build's kernel is checked in the next section.

=== one more absence from the same read, which is §12 item 12's new candidate ===

  `alsa-ucm-conf` is **absent**, 0 of 834, while `libasound2-data` — the package whose `Recommends:`
  it is — is **present**, one stanza. That is the edge measured from both ends: the recommending
  package is in the image, the recommended one is not, and `LB_APT_RECOMMENDS="false"` above is the
  reason. §12 item 12 recorded the same absence from a different source
  (logs/M1-firmware-contents-lines.txt §7, read out of the archive's Contents-derived listing); this
  is a second, independent measurement of it out of the built image's own dpkg database. Two sources
  agreeing is worth more than one, and this one is the stronger of the two because it is the image
  rather than the index. `alsa-topology-conf` being present while its companion is not is the exact
  asymmetry item 12 describes: half of ALSA's card configuration arrives because §5 names it, and the
  other half does not arrive at all.

=== limit, and it is the one §10 now carries ===

  Run K never assembled an ISO. It died in `binary_rootfs`'s teardown
  (`/usr/lib/live/build/binary_rootfs:347-362`, logs/M1-runK-rootfs-iso-failure.txt), after the
  837 296 128-byte squashfs was written but before anything was wrapped around it. So everything in
  this section was, when written, a statement about the **rootfs image** a build produced, not about
  a shipped artifact a friend could boot. The names, the kernel and the absences were unlikely to
  differ — the squashfs was already complete and frozen — but "unlikely" is not a measurement, and
  §11 does not accept one. Run M (2026-11-01T14:03:27Z) was the build that repeats this against an
  assembled ISO; when it lands, `scripts/m1-diff.sh` regenerates `logs/M1-image-installed.txt` from
  the shipped squashfs and the five lines above get re-read rather than assumed.
