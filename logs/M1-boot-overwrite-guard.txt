`harness/boot-test.sh` deleted the run it was pointed at, and the fix for that found a second bug
that had stopped the harness's own frame-capture fix from ever executing.

Why this file exists
  Task: boot-test run N's ISO (§10's M1 exit needs it, and three things are still unexercised —
  `/etc/apt/apt.conf.d/00recommends` as installed behaviour, the shift-minus underscore mapping, a
  real desktop VT). Checking the harness before pointing it at run N turned up two defects. Both
  are now fixed and both fixes have been run. Neither was found by a boot test.

=== defect 1: `rm -rf` of a caller-named directory, unconditionally ===
As the file stood, line 80-81 were:

    W="$OUTROOT/$RUN"
    rm -rf "$W"; mkdir -p "$W"

`--run` is caller-supplied and is also the filename prefix of every frame the harness writes
(`$RUN-<label>.png`). So passing a name that has been used before does not collide and warn — it
deletes that run's photographs before taking new ones, and nothing in the output mentions it.

This is the third instance of one defect class in this repo, and §11 now has a rule for the class
("A log with a fixed filename is not a log for a run"). It is the worst of the three here:

  * `/root/phantomos-tests/M1-boot` holds run M's 74 files — the only photographs of the
    no-login defect that `logs/M1-no-live-user.txt` is written from. They had not been copied
    anywhere else on the host.
  * `logs/evidence/` in the repo holds those frames under the *same* fixed names
    (`M1-boot-cmd-1.png`, `M1-boot-boot-85.png`, …). So a second `--run M1-boot` would destroy
    them on the host and then silently overwrite the repo's copies when the new frames were
    copied in. The previous run's evidence would not just be lost; it would be replaced by
    different pictures under the names the older write-ups cite.

Fix: refuse an existing non-empty run directory, name what is in it, and require
`PHANTOMOS_ALLOW_RUN_OVERWRITE=1` to go ahead — the same idiom `scripts/build-iso.sh` uses for a
non-idle work tree, so the override has to be deliberate rather than habitual. Exit 2, matching
the file's other pre-flight failures.

=== defect 2: `shot()` could not execute, and had never executed ===
Case B died immediately with

    harness/boot-test.sh: line 108: label: unbound variable

Line 108 was

    local label="$1" ppm="$W/$RUN-$label.ppm" png="$W/$RUN-$label.png" s1 s2 i

which references `label` in the same `local` that declares it. Bash expands every word of a
`local`/`declare` before assigning any of them, so `$label` is read before `label` exists. Both
faces measured on the build host rather than reasoned about:

    $ bash -c 'set -u; f(){ local a="$1" b="x-$a"; printf "%s\n" "$b"; }; f hello'
    environment: line 1: a: unbound variable          exit: 127

    $ bash -c 'set -u; a=STALE; f(){ local a="$1" b="x-$a"; printf "%s\n" "$b"; }; f hello'
    x-STALE                                           exit: 0

The second is the reason this is not merely a crash: with a global of that name in scope the
function runs, reports success, and writes the frame under the **stale** name. A harness whose
job is to produce correctly-named evidence would have produced evidence named after whatever ran
before it. No global `label` exists in this file (grepped: the only occurrences are inside
`shot()` and in two comments), so the failure mode here is the loud one — but it is one keyword
away from the quiet one.

Fix: split the declaration in two, so `$label` is only expanded after `label` is assigned.

The consequence that matters for what is already claimed: **this line was introduced by the fix
for the truncated-frame bug**, the fourth bug in the file's own header ("shot() now waits for the
size to settle and checks the converter's exit status"). That fix therefore never ran. Run M's 74
frames were taken by the pre-fix body, which is consistent with run M's log having exactly
2 MISSING frames and no settle behaviour in it — and it means the header's claim that the four
bugs were "all found by running it" was true of the finding and not of the fixing. Three of the
four were exercised by that run; the fourth was written, and wrote a bug.

=== what this does not claim ===
The settle loop has now run, but not against the condition it was written for. Run M's truncated
frames were 1280x800, i.e. 3072016-byte PPMs written while the guest was busy; this test produced
720x400 PPMs of 864015 bytes from a guest that was doing nothing. Two complete small frames show
the loop terminates and the naming is right. They do not show it catches a half-written large one.
Run N's boot test is what exercises that — 26 commands, 1280x800, and a desktop starting under
them — and if it produces MISSING or CONVERT-FAILED lines the loop is still not enough.

=== what run N's boot test must therefore do differently ===
Use a name that has not been used: `--run M1-boot-runN`. Not `M1-boot`, which is run M's and is
the evidence `logs/M1-no-live-user.txt` cites. The frames then land as `M1-boot-runN-*.png`, which
also cannot overwrite `logs/evidence/M1-boot-*.png` when they are copied in. The guard now makes
the mistake fail loudly instead of quietly, but the guard is the last line, not the plan.

=== this check is not a registered test, and that is a known gap ===
`scripts/run-tests.sh` registers two tests and neither covers `harness/boot-test.sh`. What is
above was run by hand and logged, which satisfies §11's "a run and a log" but not its registration
rule in spirit: the guard can regress and nothing would notice. Promoting it means a third test
file whose case B needs qemu on the host (cases A and C do not, since the guard fires before qemu
starts, so a qemu-free version could cover the protective branch and the override branch only).
Not written during the M1 close, because run N is the thing that has to land and the boot test
below exercises the same file for real. Recorded here so the gap is a decision rather than an
omission.
