M1 run L — the milestone-closing attempt that did not close, 2026-10-31
========================================================================

Run L was launched detached at 2026-10-31T00:43:22Z to be the cold run §9.1 requires. It did not
produce an ISO. Two independent faults stopped it, and only one of them was the network. All times
below are UTC unless they are quoted from the build log, whose `[YYYY-MM-DD HH:MM:SS]` stamps are
host-local EAT (UTC+3) — the convention §9.1 records, and the reason `04:31:53` in the log is
`01:31:53Z` here.

  launcher out : /root/phantomos-m1/logs/closing-run-2026-10-31T004322Z.out
  lb build log : /root/phantomos-m1/logs/lb-build-2026-10-31T004330Z.log  (4548 lines)
  config dump  : /root/phantomos-m1/logs/config-dump-2026-10-31T004330Z.txt (98 assignments)
  lb build     : 2026-10-31T00:43:31Z .. 2026-10-31T01:31:53Z = 48 m 22 s, then died

Raw evidence for every claim below is appended after §6, in sections A-K pulled straight off the
build host.


1. Fault one: build-iso.sh was edited while it was running, and bash died mid-script
------------------------------------------------------------------------------------

The launcher's own stdout (section A) ends like this:

    === effective config of the tree about to be built ===
      98 assignments -> /root/phantomos-m1/logs/config-dump-2026-10-31T004330Z.txt
    /mnt/c/Users/INFINITY/OneDrive/Desktop/phantomOS/scripts/build-iso.sh: line 85: syntax error near unexpected token `('
    /mnt/c/Users/INFINITY/OneDrive/Desktop/phantomOS/scripts/build-iso.sh: line 85: ` are optional (M1 ships none — see the header of scripts/build-packages.sh for why'

That second line is prose. It is the tail of this comment, which in the file is prefixed `# Hooks`:

    # Hooks are optional (M1 ships none — see the header of scripts/build-packages.sh for why

bash executes a script from one open fd and a byte offset it maintains itself, re-reading as it
goes. The artifact-loss fix (the `artifacts/` exclusion and the `find … -name '*.iso' -exec mv`
above it) was written into `scripts/build-iso.sh` while run L was inside `lb build`, and it
lengthened the file above the point bash had reached. The next `read()` landed in the middle of
that comment, bash parsed a fragment of a sentence as shell, and the shell exited. The reported
line number is bash's own counter after the jump and does not correspond to line 85 of either
version of the file — the *text* is what identifies where the offset fell.

`lb build` was already a running child, so it was orphaned rather than killed and went on for
another 40 minutes. What was lost is everything bash would have done afterwards:

  * `cp "$BUILD_LOG" "$REPO/logs/$LOGNAME"` — the build log was never copied into the repository.
    It survives only because `$WORK/logs` is excluded from `rsync --delete`; this is the second
    time that exclusion has been the only thing standing between a run and its evidence.
  * the `artifacts/$START/` move, the size, the SHA256 and `logs/M1-artifact-$START.txt`.
  * `exit $RC`, so the launcher recorded no exit status at all.

The failure was found by reading `$WORK/logs` by hand, which is exactly how §11 says a milestone
should not be closed. Fixed in `scripts/build-iso.sh`: the script now copies itself to
`$WORK/.build-iso.running.sh`, excludes that path from the rsync, and `exec`s the copy, so the
repo's version is inert data for the rest of the run.

The five `Ign:`/`Err:` pairs are `Acquire::Retries "5"` from `live/config/apt/apt.conf` doing
exactly what it was added to do after run K, and the outage outlasting it — the same conclusion
that file's header already refuses to claim otherwise.

`/usr/lib/live/build/binary_rootfs`, squashfs branch (section F):

    Check_package chroot /usr/share/doc/squashfs-tools squashfs-tools
    Restore_package_cache binary
    Install_packages

so the last thing every build does before `mksquashfs` is an apt install into the build chroot,
and that install goes to the network whenever `cache/packages.binary` does not already hold the
package.

It did not. Measured before anything was changed: `find /root/phantomos-m1/live/cache -name
'squashfs-tools*'` returned **zero** hits across all five caches, while `cache/packages.binary`
held 25 `.deb`s — `xorriso`, `mtools`, `syslinux-common`, `grub-efi-*`, `shim-*`, `dosfstools`,
`librsvg2-bin`, `gettext-base`, `isolinux`, `mokutil`, the `libburn4/libisoburn1/libisofs6/
libjte2` set. Every one of those belongs to `binary_iso` or `binary_grub-efi`, whose
`Save_package_cache binary` runs *before* their `Remove_packages`. `binary_rootfs` saves at line
378, after `Remove_packages` at 345 (section H). Whether that ordering is why its helper never
lands is **not established** — `Save_package_cache` also runs `apt-get autoclean` first, and the
`Del` lines in section K show autoclean discarding cached image `.deb`s (`linux-image` 108 MB,
`firefox-esr` 79.9 MB among them) during the binary cycle. What is established is the outcome:
the one package the build needs at its most expensive moment was the one package no cache held.

This is the same failure class as run K (`logs/M1-runK-rootfs-iso-failure.txt`), which died one
stage earlier in `chroot_archives binary remove`. Two consecutive milestone-closing attempts, both
lost to a resolver outage, both after 48+ minutes.

4. What run L measured about downloading — the answer to "would caching make this faster?"
------------------------------------------------------------------------------------------

The whole 4548-line log contains **one** `Fetched` line:

    726:Fetched 17.8 MB in 31s (580 kB/s)

and every `Get:` line in the log is an index or an entry from our own bound pool — `InRelease`,
`Packages`, `Sources`, `Translation-en`, and `file:/opt/phantomos-build/pool ./ InRelease`.
**Run L downloaded no `.deb` from the network at all.** (An earlier reading of this log counted
"10 `.deb` Get: lines" by grepping for `.deb`, which matched `deb.debian.org`; that count was
wrong and is not repeated here.)

The 17.8 MB breaks down as (section B): `trixie/main Sources` 10.5 MB, `trixie/main
Translation-en` 6486 kB, `trixie-security` InRelease/Packages/Sources/Translation 1.0 MB,
`trixie-updates` 60 kB, `trixie InRelease` and the rest. Two of those — `Sources` and
`Translation-en`, 17.0 MB of the 17.8 MB — are indices the build never reads a package out of:
`--apt-source-archives true` is in the effective config (section A) and nothing in this project
runs `apt-get source`, and `Translation-en` only supplies long descriptions.

Meanwhile `chroot_install-packages install` ran 03:53:07 → 04:04:51 (**11 m 44 s**) and installed
the whole desktop set with **no `Fetched` line at all**, because `Restore_package_cache chroot`
had already copied `cache/packages.chroot` (574 MB) into `chroot/var/cache/apt/archives` and apt
found every `.deb` on disk. `cache/packages.chroot`'s mtime is 2026-10-30 23:31 — *before* run L
started — so run L added nothing to it: the package cache was already complete and simply served
the build.

So the honest answer is that package caching is already done and already total. The wall clock
went somewhere else. From the stage timestamps (section B):

    bootstrap_debootstrap        03:43:32 → 03:51:42    8 m 10 s
    chroot_archives install #1   03:51:59 → 03:52:56       57 s
    chroot_install-packages      03:53:07 → 04:04:51   11 m 44 s   (no download)
    chroot_archives remove  #1   04:05:47 → 04:09:52    4 m 05 s
    chroot_archives install #2   04:10:33 → 04:19:00    8 m 27 s
    chroot_archives remove  #2   04:19:01 → 04:23:02    4 m 01 s
    chroot_archives install #3   04:23:37 → 04:31:53    8 m 16 s   (binary cycle)
                                                          -------
                     five chroot_archives invocations    25 m 46 s  of the 48 m 22 s

Over half the run was `chroot_archives`, i.e. `apt-get update`, and since almost nothing was
downloaded, that time is apt *parsing and caching* the same 17 MB of indices five times on a
2016 dual-core i5-6200U — plus, in the last two cycles, retries against a resolver that was
already failing (`Ign:` ×100, `Err:` ×20 across the log). A caching proxy does not remove parsing
cost; removing the two unread indices does.


5. What was changed as a result
-------------------------------

* `scripts/seed-binary-cache.sh` (new). Derives the package from `binary_rootfs`'s own
  `Check_package` line and its dependencies from `apt-cache depends`, downloads them with
  `apt-get download`, and copies them into `$WORK/live/cache/packages.binary` so
  `Restore_package_cache binary` serves them from disk. It refuses to copy if the filename
  `apt-get download` produced differs from the filename apt itself used during a real install,
  because apt only reuses a cached `.deb` whose name is the one it would have downloaded. That
  check was not decoration: it showed the convention is mixed — `liblzo2-2_2.10-3+b1_amd64.deb`
  with a **literal `+`**, matching the file `Save_package_cache` moved out of a live chroot, while
  the epoch is encoded, `squashfs-tools_1%3a4.6.1-1_amd64.deb` and
  `zlib1g_1%3a1.3.dfsg+really1.3.1-1+b1_amd64.deb`. Run L's error text quoted
  `liblzo2-2_2.10-3%2bb1_amd64.deb`, which is the *URI* form, not the on-disk form; seeding from
  the URI would have produced files apt never reads. Output: `logs/M1-binary-cache-seed.txt`.
  After it ran, `cache/packages.binary` holds 32 `.deb`s, 19 MB.

  The seed is build-side only. `squashfs-tools`, `xorriso`, `mtools` and `dosfstools` are all
  absent from `logs/M1-image-installed-raw.txt`, the 838 packages dpkg reports inside the shipped
  squashfs; `liblzo2-2` is present there because the image needs it independently.

  Residual exposure, not hidden: apt reuses a cached `.deb` only when it matches the candidate
  version, so a Debian release between the seed and the build's own `apt-get update` reopens the
  hole for that one package. The seed is additive and re-derived each run, so the window is the
  time since the last seed rather than permanent.

* `scripts/build-iso.sh` now re-execs a private copy of itself under `$WORK` (§1 above).

**Proven by run, not yet.** The seed's claim — that `binary_rootfs` installs `squashfs-tools`
without touching the network — is confirmed or refuted by the next build log: it must contain no
`Get:`/`Ign:`/`Err:` line naming `squashfs-tools` and must reach `P: Preparing squashfs image...`.
Until that log exists this file records an intention with a mechanism, not a result.


6. Also recorded here because it is the second time
----------------------------------------------------

`rsync --delete` in `build-iso.sh` has now twice been the only reason a run's evidence survived:
once for the pool-ordering failure log (§9.1), once here for `lb-build-2026-10-31T004330Z.log`.
`$WORK/logs` being excluded is load-bearing, and it is easy to break by tidying the exclusion
list. Run output goes under `$WORK/logs` with timestamped names for that reason and no other.

Restore_package_cache ()
{
	local DIRECTORY="cache/packages.${1}"

	if [ "${LB_CACHE}" = "true" ] && [ "${LB_CACHE_PACKAGES}" = "true" ]
	then
		if [ -e "${DIRECTORY}" ]
		then
			# Restore old cache
			if [ "$(stat --printf %d ${DIRECTORY}/)" = "$(stat --printf %d chroot/var/cache/apt/archives/)" ]
			then
				# with hardlinks
				find "${DIRECTORY}" -name "*.deb" -print0 | xargs -0 --no-run-if-empty cp -fl -t chroot/var/cache/apt/archives
			else
				# without hardlinks
				find "${DIRECTORY}" -name "*.deb" -print0 | xargs -0 --no-run-if-empty cp -t chroot/var/cache/apt/archives
			fi
		fi
	fi
}

Save_package_cache ()
{
	local DIRECTORY="cache/packages.${1}"

	if [ "${LB_CACHE}" = "true" ] && [ "${LB_CACHE_PACKAGES}" = "true" ]
	then
		# Cleaning current cache
		# In case of interrupted or incomplete builds, this may return an error,
		# but we still do want to save the cache.
		Chroot chroot "apt-get autoclean" || true

		if ls chroot/var/cache/apt/archives/*.deb > /dev/null 2>&1
		then
			# Creating cache directory
			mkdir -p "${DIRECTORY}"

			# Saving new cache
			local PACKAGE
			for PACKAGE in chroot/var/cache/apt/archives/*.deb
			do
				if [ -e "${DIRECTORY}"/"$(basename ${PACKAGE})" ]
				then
					rm -f "${PACKAGE}"
				else
					mv "${PACKAGE}" "${DIRECTORY}"
				fi
			done
		fi
	else
		# Purging current cache
		rm -f chroot/var/cache/apt/archives/*.deb
	fi
}
